# GuideOS 0.4.2.02

Interface follow-up for installed 0.4.2.01. Signed sequence 61, compatible base
sequence 60. This revision changes the signed Python/interface generation and
adds one immutable graphic; it needs no new native library or host service.
The complete package is suitable for the existing Wi-Fi delivery path.

## Audio and Media

Settings → Audio now opens an Audio page. It reports the selected provider output
and volume and offers Current audio output, Bluetooth earbuds and Refresh audio
information. Existing provider operations own output selection, pairing and
discovery. B from a subpage returns to Audio; B from Audio returns to Settings.
Physical volume controls remain global and music keeps playing when leaving.

Media / Library contains only Music and Video. Library and selection pages use
their own short notices, with no appended player position or playback message.
Native playback status remains separate from the audio provider's status and
cannot overwrite Audio command notices. No new output or pairing authority is
introduced by moving the controls.

## Pending launches and replay

Media catalogue lookups and open requests carry a shell-owned launch generation.
Back, Home, Power, subview navigation and replacement selections invalidate the
previous generation, discard queued launch work and ignore its late catalogue
responses, including failures and pagination. Established background audio is
preserved when only an unresolved lookup or an unsent open is cancelled.

An open already sent to the native player is followed by a serialized stop
barrier. A replacement lookup/open waits behind that barrier. Video display
ownership remains held until a stopped/non-video acknowledgement or bounded
service recovery completes; recovery failure retains ownership and the newer
intent. The shell also recognizes display return when a queued video is cancelled
within one input iteration. These mechanisms implement existing shell navigation
and media lifecycle responsibilities; they do not introduce new provider grants.

Both the A control and the displayed player action now use Pause for active
playback, Resume only for paused playback and Play after Stop or completion.
Play reopens the selected catalogue ID and generation through the ordinary open
path, including video display admission and existing card/output checks. The
backend's rejection of inactive pause/resume/seek remains unchanged. Opening
controls are disabled while lookup/open is pending; Play without a selection
cannot submit a request. The Video status screen now renders its primary action
as a visible hit target, using the shared facts-screen action renderer.

## Video display handoff

The GPU restored its saved framebuffer during handoff; that buffer could still
contain Home's initial image. Before restoring scanout, the shell now writes a
fresh transition image into that framebuffer, then releases the display. Video
uses `assets/opening-video.png`: a prebaked 640×480 dark graphic with centered
“Opening Video” at 48 pixels in DejaVu Sans, the current GuideOS renderer's face
and the documented reduced `guide-sans` face. It has no chrome or status overlays.
The asset is decoded and cached during shell initialization, not rasterized on
each open. Browser handoff also refreshes its recovery frame.

## Browser entry and return-from-media correction

The fresh capture was made on installed 0.4.2.01. The browser acquired the
display, but the owner could not enter/submit an address. The Keys button inferred
its target from `Gtk.Entry.has_focus()` after button activation; GTK 4 delegates
entry focus to its internal text widget, and activating a button also moves
focus. The resulting page-target keyboard could submit text to a blank page
instead of navigating.

The browser now opens an address keyboard on a blank first page, has an explicit
Address button and Go action, and keeps Page keys explicitly separate. Address
editing starts with the current address. Character/edit controls restore draft
entry focus; either Go submits that draft. Initial `about:blank` events preserve
the address keyboard. Default keyboard target selection recognizes internal
entry focus. Failed loads report only a bounded error domain/code in diagnostics,
with no addresses or page/user text. Network and website permission policy stays
with the existing providers.

The same capture records a shell ValueError after Media returned to Files. The
actual details renderer reproduces that error at the start of its animation:
an action button's translated left edge exceeds its fixed right edge. Such
offscreen actions are now skipped until drawable, while hit targets still wait
for the panel's existing animation admission threshold. All 101 sampled
animation frames rendered, and the completed panel retains both action targets.
The capture's original traceback hid source frames, so matching this reproduced
failure to that particular crash remains an inference. Future shell failures
record a bounded list of trusted module/line/function fields without exception
bodies or input data.

While the browser owned the display, captured shell polling ran roughly 1,700
iterations per second and used about 90% of one core. The shell had a pending
draw revision but could not advance its draw deadline while leased. Leased
display input polling now waits up to 1/60 second, waking on real input, instead
of repeatedly using the expired deadline. Actual CPU improvement remains a
post-installation observation.

Real host GTK/WebKit address submission loaded two loopback HTTP fixture pages
through both Go controls. The current layout fits 640×480. These are development
host checks, not Deck controller or Internet navigation acceptance. Receipts:
`browser-entry-inspection.json`, `browser-layout-inspection.json`, and
`details-animation-inspection.json` under `build/release-0.4.2.02`.

## Desktop preparation workflow

HandBrake GUI 1.10.2 was already installed. Its matching official CLI is installed
under `%LOCALAPPDATA%\Programs\HandBrakeCLI` and added to the user's PATH. The
download's SHA-256 matched the official release asset digest:
`f0fc3b1c3c4b7a24618417ff6a1f50e2158ad9dab68717f7997c2ea3a5895004`.

NDI 1.0.3 adds Prepare video under Shared media. It uses the exported
`node/desktop/presets/GuideOS-Deck-480p30.json` profile, usable in both HandBrake
interfaces. Choose a source and a different destination; conversion runs locally
on the desktop and does not require a connected Deck or grant sharing access.
Cancel/close terminates the owned encoder with bounded waits. An unfinished file
uses a non-media suffix and is published only after successful conversion.
Existing source and destination files are never silently replaced. This does
not transcode on the Deck or change its selected audio output.

Profile: MP4, H.264 Constrained Baseline level 3.0, one reference frame, no B frames,
fastdecode tuning, square pixels, aspect preserved within 640×480, no automatic
crop, at most 30 fps, RF 23 with a 1.5 Mb/s video ceiling/3 Mb buffer, and stereo
AAC-LC at 128 kb/s and 48 kHz. These are initial board preparation choices, not
measured universal playback limits. Rendering a full-HD source at a smaller
display size does not make it a smaller source to decode.

The supplied clip is 1920×1080 H.264 Main level 4.1 at 30000/1001 fps, about 7 Mb/s
video plus 317 kb/s AAC audio, and 17,554,571 bytes. The prepared copy is 640×360
Constrained Baseline level 3.0 at the same frame rate, about 223 kb/s video plus
128 kb/s audio, and 861,113 bytes. Encoded frame area is one ninth of the original;
this does not imply a measured ninefold CPU improvement. Duration remains about
19.2 seconds. The desktop source remains intact.

## Evidence and delivery state

Current source compilation, representative Audio/output/Bluetooth/Library renders
and navigation checks passed. Audio returns to Settings and Media has only two
choices. The actual HandBrake CLI imported the exported profile and successfully
prepared the clip; metadata confirms its format, size, timing and audio. NDI's
Windows executable built. No test suites or playback experiments were run.

The current media transition inspection manually delivered delayed provider
replies into the source panel and exercised real shell navigation and rendered
hit targets. It covered B/Menu/Power cancellation, pagination, stale success and
failure, queued and in-flight opens, stop/recovery acknowledgement, replacement
launch ordering, background audio preservation, and music/video replay through
both A and the visible Play action. Source compilation and stopped-player renders
passed. See `build/release-0.4.2.02/media-transition-inspection.json`. Provider
replies were simulated; hardware display release, source removal, output failure
and physical replay acceptance remain open.

The external card was identified as the Transcend USB reader containing a
250,399,948,800-byte card with GUIDE/exFAT and its existing `GUIDE/MEDIA` directory.
The optimized clip was written as a new `- Deck.mp4` file. Its complete readback

not a Seed/root write.

The signed 0.4.2.02 package is verified against the installed 0.4.2.01 trust and

0.4.2.02/sequence 61; the received file identity matches the local bundle.
See `build/release-0.4.2.02/wifi-delivery.json` and `wifi-stage.json`.

The owner performed the local Deck install action. Live status now confirms
0.4.2.02/sequence 61, transaction committed, and a ready shell running the exact
received release. The old shell exited cleanly; the new GPU shell recorded
`shell_ready` at monotonic 1256.614749 without a subsequent crash in the retrieved
service journal. See `wifi-installation-status.json` and `wifi-delivery.json`.

The owner saw an unreadable error. The transaction retains
`external-power-required` from an earlier admission failure even though it is

or bypass was attempted. Smoothness, audio continuity, Deck address entry and
