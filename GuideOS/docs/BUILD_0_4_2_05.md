# GuideOS 0.4.2.05

Owner-approved performance integration following the working-source review of
0.4.2.04 on 2 October 2026. This is a development candidate. Accepted Home,
media layouts, Settings explanations and semantic A/B controls are preserved.

## Implementation limits

New playback admission expires inventory after 10 seconds; discovery failures
retain last-known rows as unknown rather than manufacture removal. Decoder output
remains pinned; this does not authorize migration. Directory snapshots expire
after 10 seconds as a backstop to change notifications. Scan cancellation is
checked between entries and before publication; Python cannot preempt a kernel
filesystem operation already in progress.

Text caching retains existing wrapping and compositing, including correct Cairo
alpha/color-glyph conversion. Direct Cairo pixel transfer and alternate cold
Pango wrapping are deferred until visual equivalence is established. The current
PNG conversion runs only on a raster cache miss. Stable GPU viewports still use
CPU image comparison; fully separate stationary layers remain a later refinement.

Production cgroup CPU weights, board memory limits, decoder thread counts and
hardware decoding are not guessed from development-host timings. The existing
native GPU path, three-thread software video decode, software fallback and display
lease recovery remain. Per-core CPU, input p95/p99, GPU uploads, decoder drops,
thermal/power behavior and physical display handoff require measurements on the
Deck before further resource-policy changes.

## Evidence

The focused source group passed 115 checks, storage passed 41 checks including
the provider socket and UI retry path, and the ARM64 audio group passed 14 checks.
Each group had zero failures, errors or skips. This is not a complete repository
suite: two known legacy Wi-Fi shell fixtures remain excluded, and older broad
UI fixtures have assumptions that differ from the current accepted layouts.
The full audio tone-generation suite exceeded its emulation deadline; the focused
ARM64 group does not claim full audio or physical output acceptance.

There were 120 matching pixel/control comparisons against the frozen 0.4.2.04
layouts, including Home, long-name media/details and Settings. In the 30-frame
development-host scrolling sample, raster calls fell from 510 to zero and
measurement calls from 18,728 to 20. These are host work counts, not Deck speed,
battery or thermal measurements. The ARM64 native compositor compiled with strict
warnings enabled. Bounded discovery checks verified successful, oversized and
stalled child-process cleanup.

The offline image verification record is kept with the candidate in
`build/release-0.4.2.05/candidate/`. Verification passed installed signature checks,
all 16 staged source/library hashes, the filesystem check and a whole-tree
comparison allowing only the intended release/runtime changes. Owner state,
homes, network credentials, configuration, SSH identities and retained journals
match the saved baseline. ARM64 emulation passed real private D-Bus callback and
variant-signature checks, real mpv status/seek/EOF behavior, the 14 installed audio
checks, and native Pango rendering/library ABI checks. Display scanout and audio
hardware were not exercised. The harness uses explicit ARM64 child launchers and
Linux temporary storage for private sockets; neither is a production runtime change.
The signed UI archive is an internal image payload, not a standalone network
update: it requires sequence 64 and rejects the existing sequence 63 because it
depends on updated system runtime files. Full runtime rollback requires the saved
full image; selecting the previous UI release alone does not restore those files.
Storage asynchronous listing is opt-in so the previous UI's synchronous calls
remain compatible.

Source, signed payloads, offline image verification, Seed readback and physical
acceptance are separate evidence levels. At this baseline stage no connected Seed had been written. The saved
0.4.2.04 image was an offline packaging baseline, not a fresh capture of current
owner state. The subsequent owner-authorized deployment is recorded below.

## H700 Cedrus development addition

Option 2 is integrated in the working source and isolated native build:
[implementation, provenance and acceptance](../board/rg35xxh/debian/cedrus/README.md).
The addition pairs a GuideOS Linux 7.2.7 Cedrus driver, H700 device trees and
matching modules with private FFmpeg 9.0/mpv 0.41.0. The external controls module
is also rebuilt for the new kernel release. It preserves existing board patches,
the native media service, display/audio ownership and three-thread software recovery.

Hardware admission checks runtime integrity and matched accessible Cedrus devices
once per open. Only H.264 requests the copy-back decoder; other codecs retain
software decoding. Missing/incomplete runtime, mismatched kernel and unavailable
devices keep the system player. Actual decoder use remains observed IPC evidence.
No global media library or libc replacement, new service or network access is added.

The focused source group now passes 127 checks. Native and kernel build receipts
are under `build/release-0.4.2.05/cedrus/` and `cedrus-runtime-result.json`.
Physical boot, actual Cedrus decode, GPU output, memory envelope and display/audio
handoff remain acceptance gates. No speed, thermal or battery improvement is claimed.
The previously verified image and signed UI payload do not contain this addition.
Full-image packaging must include the kernel, DTBs, complete modules and private
runtime together before an owner-authorized deployment. The subsequent
boot/root deployment is recorded below; physical behavior remains unaccepted.

The isolated build passes kernel/device-tree verification, matching Cedrus and
external controls module release checks, and preservation checks for audio, MMC
and Panfrost source. ARM64 emulation over the saved read-only image enumerates
the H.264 Request decoder and passes real 640 x 480 H.264 playback with requested
hardware decoding falling back to software when no device is present. Pause,
seek, readiness, EOF and status without extra IPC requests pass. GPU/DRM and
PipeWire outputs are compiled and enumerated; physical scanout/audio were not
exercised. The private launcher's real process-boundary test preserves the media
descriptor and scopes its library path to the player.


## Returned Seed deployment, 2 October 2026

The owner requested writing the newest candidate to the inserted Seed. The system
was rebuilt from this returned card's fresh capture, with the approved performance
changes, GPU video observation/recovery and coherent H700 Cedrus addition together.
GuideOS is 0.4.2.05, sequence 64, with kernel `7.2.7-guide-cedrus0`.
System media remains the descriptor/display/audio owner; only H.264 can request
the private decoder. Actual decoder use remains observed device evidence.

The deployment candidate and receipts are in
`build/release-0.4.2.05/deployment-candidate/`; fresh recovery captures are in
`build/release-0.4.2.05/returned-seed-deploy-20261002/`. The older `candidate/`
directory remains a historical baseline and must not be substituted for this image.
The internal signed UI archive still requires sequence 64 and cannot install the
kernel/system runtime through a standalone Wi-Fi update.

To fit the existing partition without changing geometry or deleting owner state,
the installation copy strips module debug data and uses XZ compression. Every
module retains its executable text and matching release; the original unstripped
build stays on the development PC. The installed ARM64 kmod reads both compressed
Cedrus/joypad modules and resolves their dependencies. Only the two regenerable
APT lookup cache files were removed. All earlier kernels/releases are retained.

Verification covers both filesystems, installed signatures/payloads, source hashes,
whole-tree bounded changes and exact owner-state preservation. Real ARM64 emulation
passes private D-Bus, system and private-player pause/seek/readiness/EOF/software
fallback, installed audio checks, kmod compression/dependencies and Pango/native
compositor boundaries. It does not exercise hardware scanout, audio or decoding.

The bounded writer rediscovered the card by full identity and exact geometry,
matched the fresh captures immediately before writing, then wrote only the FAT
boot partition and root partition. Full readback of both equals the verified
candidate. The first MiB containing bootloader/partition table, data partition
and retained tail region match their original hashes. Every retained boot file,
including configuration, diagnostics and prior Image backup, is preserved; only
Image and the two device trees changed. Root homes, credentials, configuration,
SSH identities, application state and journals remain identical to the fresh capture.

The first attempt completed and flushed root, then Windows denied direct boot
access because its FAT volume was open. Its transcript and prewrite audit are
retained. A separate bounded completion pass verified the new root and unchanged
original boot/data/head/tail, rediscovered the boot-volume GUID from this exact
Seed, checked its physical extent, acquired an exclusive volume lock and
dismounted it before writing only that partition. Both complete partitions were
then read back again; no system rewrite or alternate target was used.
Windows rejected FlushFileBuffers on the dismounted logical-volume handle after
the complete boot byte count. A final helper issued no region writes: it verified
the interrupted-attempt evidence, flushed through the physical card handle,
reopened the card for reading, and verified full root/boot plus preserved regions.
Both failed transcripts, both write audits and the final readback transcript are
retained. The final receipt, rather than byte counts, establishes completion.

Later on-device reports and authenticated diagnostics confirm boot and Panfrost
GPU shell rendering, but expose omitted exFAT/UTF-8/uinput drivers and incorrect
Node A focus dispatch. See [the 0.4.2.06 repair](BUILD_0_4_2_06.md). The original
candidate verification did not cover these installed-service requirements.

Card readback is confirmed. Complete physical controls, selected-route audio,
external-card reinsertion, actual Cedrus/GPU use and repeated display return remain
pending on-device acceptance. No performance, thermal or battery result is claimed.
